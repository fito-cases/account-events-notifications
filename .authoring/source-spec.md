# Source specification — Account Events Without Notification Coupling

## Project
Greenfield Java 21 / Maven 3 account model for the retail banking operations ticket in `.case/situation/01_intro.md`. The branch carrying `.case/` is the starter (target branch `v1.0.0`); `case/solution-v1.0.0` is the local worked solution. Create `pom.xml`, `.gitignore`, `src/main/java/account/` (account, transactions, event/subscription contracts, recipients, delivery implementations) and `src/test/java/account/` (transaction and notification tests). No framework dependency is necessary for the Observer collaboration: a publisher holds registered subscribers and invokes their shared callback, with event context identifying the account and completed state. Registration and removal are dynamic; subscribers can be selected per event, multiple recipients can subscribe, and the publisher knows no concrete recipient, SMS, or WhatsApp type. The composition outside `CurrentAccount` associates the account owner with overdraft, account manager with the R$5,000-to-under-R$10,000 withdrawal band, digital security with withdrawals of at least R$10,000, and investment management with incoming-balance crossings. Separate SMS and WhatsApp implementations render/deliver notifications outside the account. No actual network provider or credentials are needed: in-memory delivery fakes capture rendered messages for tests.

Use exact cents (`long` minor units with overflow/positive-amount guards, or exact `BigDecimal`) and document whether the negative-limit magnitude is an inclusive bound. Successful operations alone change balance and publish relevant events *after* the state change; rejected transactions leave balance and subscribers untouched. An overdraft event requires old balance >= 0 and new balance < 0. Withdrawal bands refer to the individual successful withdrawal amount, regardless of resulting balance, from cash withdrawal, payment, transfer, or Pix. Investment crossing requires old balance < R$50,000 and new balance >= R$50,000 after a successful deposit, incoming transfer or incoming Pix. A single successful withdrawal may trigger both overdraft and its withdrawal-band event. All emitted message content identifies event name, customer name, CPF, branch, account number and resulting balance.

## Starter state — branch carrying `.case/` (`v1.0.0` target)
A compilable baseline `CurrentAccount` with functioning transaction validation, exact arithmetic and negative-limit rule, and unchanged production API for the eventual solution. Registration and channel/recipient seams may exist, but the event-publication behavior is incomplete: no successful transaction actually notifies registered recipients. Do not put completed event logic, worked solution notes or sender-dependent account code into starter. Two named tests in `src/test/java/account/AccountEventsTest.java` exist and fail for the specified incomplete behavior:

- `testRecipientThresholdBoundaries`: expected registered recipient events at overdraft, per-transaction withdrawal R$5,000 / R$10,000 and incoming R$50,000 boundaries, but starter emits none. First assertion emits `Expected registered account-event notification`.
- `testNotificationContentAndCompletedBalance`: expected a delivered notification containing event, customer and account details and post-transaction balance, but starter emits none. First assertion emits `Expected completed-balance notification`.

These two bullets are concrete realizations of the two descriptive `failing_tests` entries in `.case/starter_state/known_state.yaml`; that file gives no existing test identifiers and **no known-error text**. Do not claim its test names or error strings are verbatim contract text. `mvn -B clean test` builds/compiles successfully but exits nonzero because exactly these two tests fail, with no other failures or errors. `mvn -B -Dtest=CurrentAccountBaselineTest test` passes and verifies transaction success/rejection and the negative-limit rule. Tests describe observable banking behavior, not the internal implementation.

## Solution state — `case/solution-v1.0.0`
Every test passes with one-to-many per-event registration, recipient routing, independent SMS and WhatsApp channels, correct event/message fields, exact boundaries, completed state visible during notification, and no emission for rejected transactions. Deliverables: changed account activity implementation preserving the negative-limit rule; tests of success/rejection, threshold and recipient boundaries, content and completed balance.

**Rubric gates:** `.case/rubric.yaml` contains five AI-evaluated criteria (`observer-collaboration`, `sender-independence`, `event-recipients`, `notification-context`, `completed-state`); it declares **no automated or hybrid gate commands or passing conditions**. Do not attribute a fabricated command to the rubric. Project verification commands supplied by this source plan (not rubric gates): `mvn -B clean test` exits 0 with all tests passing; `mvn -B package` exits 0 and produces a JAR. Inspect account imports/fields and message capture to substantiate the AI criteria.

## Constraints
Use English class/method names; preserve the negative-limit rule; currency thresholds must not drift due to floating-point rounding; rejected transactions never emit events. `CurrentAccount` must not send messages or depend on concrete SMS/WhatsApp senders. Model the pattern as the subscription + shared callback + one-to-many delivery collaboration, not just a listener interface; do not publish irrelevant internal mutations or require an asynchronous broker. Avoid exposing pre-transaction state to synchronous subscribers. Neither tests nor starter source should contain a ready-made replacement for the missing publisher logic.
